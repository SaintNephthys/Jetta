# JETTA

브라우저에서 실행하는 반응형 게임 모음입니다. 사칙연산 게임은 덧셈, 뺄셈, 곱셈, 나눗셈과 Easy·Medium·Hard·Custom 난이도를 제공합니다. 화면 문구는 영어이며, 사칙연산 설정 화면은 연산 기호, 난이도 표시, 재생 아이콘을 중심으로 구성합니다. 아이콘 컨트롤에는 스크린 리더용 이름을 제공합니다.

메인 페이지 `index.html`의 게임 카드를 선택하면 전용 페이지 `games/arithmetic.html`로 이동하며, 게임 유형 선택 창이 열립니다. 라이트 모드는 하늘색 테마를 사용합니다. 다크 모드는 거의 검은 배경과 밝은 네온 시안 UI, 분홍색 포커스 표시를 사용해 글자와 컨트롤의 대비를 높였습니다.

- **Question goal**: 문제 수를 1–200개로 지정하고 완료 시간을 측정합니다. **10 / 30 / 50문제** 프리셋을 제공합니다.
- **Time challenge**: 시간을 10–3,600초로 지정하고 제한 시간 동안 제출한 문제 수와 정답 수를 측정합니다. **30 / 60 / 90초** 프리셋을 제공합니다. 앱이 백그라운드로 이동해도 시간은 계속 흐릅니다.

첫 진입에서 유형을 선택한 후에는 `⇄` 버튼으로 두 모드를 즉시 전환합니다. 선택 창을 다시 열지 않습니다.

프리셋을 누르면 입력값과 선택 표시가 함께 갱신됩니다. 직접 다른 값을 입력할 수 있으며, 모드를 변경해도 각 모드의 설정값은 유지됩니다.

난이도 버튼은 **Easy → Medium → Hard → Custom** 순서입니다.

- **Easy**: 기존 Medium 범위입니다. 기본 수는 10–50, 곱셈의 둘째 수와 나눗셈의 나누는 수는 2–12입니다.
- **Medium**: 기존 Hard 범위입니다. 기본 수는 20–99, 곱셈의 둘째 수와 나눗셈의 나누는 수는 2–20입니다.
- **Hard**: 기본 수는 100–999이며, 곱셈의 둘째 수와 나눗셈의 나누는 수는 10–99로 커집니다.
- **Custom**: Hard 오른쪽에 있으며, 선택하면 아래에 **Max digits** 설정이 부드럽게 펼쳐집니다. 최대 자릿수를 **1–12** 중 하나로 정합니다. 두 수의 자릿수는 각각 1자리부터 이 최댓값 이하에서 섞어 출제하므로, 항상 최대 자릿수로만 나오지는 않습니다. 다른 난이도에서는 설정이 접히고 비활성화되며, Custom으로 돌아오면 값을 유지합니다.

모든 난이도에서 뺄셈은 음수 없이, 나눗셈은 정수 답으로 출제합니다. 기본 난이도의 나눗셈은 기본 수를 몫으로 삼아 나누는 수와 곱해 피제수를 생성합니다. Custom에서는 나눗셈의 피제수와 제수가 모두 설정한 최대 자릿수 이내가 되도록 생성합니다. 사용자에게 첫 수·둘째 수의 자릿수를 따로 지정하거나 순서를 맞추도록 요구하지 않습니다.

12자리 곱셈의 답은 최대 24자리입니다. 큰 정수는 `BigInt`로 계산·비교하고, 답안은 문자열로 받아 일반 부동소수점 숫자로 변환하면서 정밀도를 잃지 않도록 처리합니다. 입력란과 결과 화면도 이를 지원합니다. 저장소에는 큰 정수 답안 대신 완료 요약만 기록합니다. 운영체제의 동작 줄이기 설정을 사용하면 펼치기·접기 애니메이션은 생략합니다.

완료 후 정답률, 제출한 문제 수, 소요 시간, 문제당 평균 시간과 연산별·문제별 결과를 확인할 수 있습니다. 최근 완료 기록과 테마 설정은 해당 브라우저의 로컬 저장소에만 저장됩니다.

게임 화면은 데스크톱, 태블릿, 모바일, 폴더블의 좁은 커버 화면에 맞춰 배치됩니다. `VisualViewport`의 크기와 위치 변화를 반영해 소프트 키보드 위의 보이는 영역에 문제와 입력란을 배치하며, 안전 영역과 지원 브라우저의 폴더블 화면 분할 정보를 반영합니다. 매우 낮은 화면에서는 진행 막대를 숨기고 스크롤을 허용합니다. 키보드의 실제 동작은 기기와 브라우저에 따라 달라 실기기 확인이 필요합니다.

## 로컬 실행

`index.html`을 브라우저에서 직접 열거나, 프로젝트 루트에서 `python3 -m http.server 8000`을 실행하고 `http://localhost:8000`을 엽니다. 상대 경로의 일반 스크립트를 사용하므로 별도 빌드 없이 파일 직접 실행과 정적 호스팅에서 동작합니다.

개발·검증에는 Node.js 18 이상과 npm이 필요합니다.

```sh
npm ci          # 개발 도구 설치
npm test        # 산술·세션·페이지 및 DOM 동작 테스트
npm run check   # Prettier 포맷 검사
npm run format  # 코드 포맷 적용
npm run build:pages # 공개 파일만 artifacts/pages/에 구성
npm run deploy:prepare # 의존성 설치 → 포맷 검사 → 테스트 → 배포 파일 생성
```

테스트는 문제 생성, 두 모드의 종료 조건과 마감 시각, 프리셋과 직접 입력, 파일 직접 실행, 페이지 이동 경로, 테마 및 키보드 뷰포트 처리, 최대 12자리 출제와 24자리 정답 채점, 다크 테마 색상 대비를 검증합니다. DOM 테스트는 jsdom에서 실행하므로 실제 화면 배치나 기기 키보드를 검증하지는 않습니다. 모바일·태블릿·폴더블과 키보드가 열린 상태의 최종 배치는 실기기 브라우저에서 확인해야 합니다.

## 코드 구조

- `index.html`: 게임 목록과 전용 페이지 링크
- `games/arithmetic.html`: 사칙연산 설정·게임·결과 화면
- `css/style.css`: 하늘색 테마 변수와 공통 컴포넌트
- `css/home.css`, `css/arithmetic.css`: 페이지별 스타일
- `js/theme.js`, `js/storage.js`: 공통 테마와 저장소 접근
- `js/arithmetic/math.js`, `session.js`: DOM과 독립된 문제 생성 및 게임 진행
- `js/arithmetic/settings.js`: 유형 선택, 프리셋, 설정 검증
- `js/arithmetic/view.js`: 문제·진행·결과·기록 렌더링
- `js/arithmetic/viewport.js`: 소프트 키보드 및 화면 크기 변경 대응
- `js/arithmetic/controller.js`: 화면 전환, 입력 이벤트, 타이머 수명 관리
- `tests/`: Node.js 테스트와 jsdom 통합 테스트

브라우저 스크립트는 `globalThis.Jetta` 네임스페이스를 사용합니다. 테마는 첫 화면 표시 전에 적용하고, 나머지 스크립트는 HTML에 선언한 순서대로 `defer` 실행합니다. 메인 페이지에서는 게임 코드를 불러오지 않습니다. 새 게임은 `games/`에 페이지를 추가하고 전용 스크립트·스타일을 분리하세요.

## GitHub Pages 배포

`.github/workflows/pages.yml`은 push와 pull request에서 `npm run deploy:prepare`를 실행합니다. 이 명령은 `scripts/deploy-pages.sh`를 통해 `npm ci` → 포맷 검사 → 테스트 → 공개 파일 패키징을 순서대로 수행하며, 하나라도 실패하면 즉시 중단합니다. 검증이 성공한 **원격 저장소의 기본 브랜치**에서만 GitHub Pages에 자동 배포합니다. 다른 브랜치나 PR에서는 배포하지 않으며, 기본 브랜치의 **Actions → Validate and deploy Pages → Run workflow**에서도 다시 실행할 수 있습니다.

배포 준비 스크립트는 저장소 루트 외의 경로에서 호출해도 자체 위치를 기준으로 동작합니다.

```sh
npm run deploy:prepare
# 또는
./scripts/deploy-pages.sh
```

로컬 실행은 `artifacts/pages/`를 준비하는 단계까지 수행하며 사이트를 게시하지 않습니다. GitHub Actions에서는 `GITHUB_OUTPUT`에 `artifact_path`를 기록하고 단계 요약을 생성합니다. 다음 단계는 이 경로만 업로드하며, 실제 게시는 `actions/deploy-pages`가 처리합니다. 스크립트에는 별도 배포 토큰을 넣지 않습니다.

최초 연결 시 한 번 설정합니다.

1. GitHub에 저장소를 준비하고 주소를 확인합니다. Pages를 지원하는 저장소·요금제여야 합니다.
2. 원격 저장소를 연결합니다. 아래 `OWNER/REPOSITORY`를 실제 값으로 바꾸세요. 이미 `origin`이 있다면 새로 추가하지 말고 먼저 주소를 확인합니다.

   ```sh
   git remote add origin https://github.com/OWNER/REPOSITORY.git
   ```

3. GitHub 저장소의 **Settings → Pages → Build and deployment → Source**에서 **GitHub Actions**를 선택합니다. GitHub Actions가 저장소 정책에서 허용되어 있어야 합니다.
4. 현재 로컬 브랜치는 `master`입니다. 배포하려는 브랜치와 GitHub 기본 브랜치가 같은지 확인한 뒤 push합니다.

   ```sh
   git push -u origin master
   ```

5. **Actions → Validate and deploy Pages**의 성공 여부와 `github-pages` 환경의 배포 URL을 확인합니다. 이후 기본 브랜치에 push하면 검증 후 자동 배포됩니다.

브랜치가 `main` 등으로 바뀌어도 원격 기본 브랜치를 기준으로 판단하므로 워크플로 수정은 필요하지 않습니다. 워크플로가 통과했는데 배포 작업이 건너뛰어졌다면 push한 브랜치가 기본 브랜치인지 확인하세요. `github-pages` 환경에 승인·브랜치 보호 규칙이 있다면 해당 규칙도 충족해야 합니다.

설정에는 GitHub에서 실행 시 제공하는 기본 토큰을 사용하며 별도 PAT나 비밀값을 소스에 넣지 않습니다. 검증 작업은 저장소 읽기 권한으로 실행하고, 배포 작업에만 `pages: write`와 `id-token: write`를 부여합니다. 공식 절차는 [GitHub Pages 사용자 지정 워크플로 안내](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)를 참고하세요.

배포 스크립트 `scripts/build-pages.js`는 `index.html`과 `games/`의 HTML, `css/`의 CSS, `js/`의 JavaScript만 `artifacts/pages/`로 복사합니다. 숨김 파일·환경변수·키 파일·개발 의존성·테스트·문서·Git 메타데이터는 배포 대상에 포함하지 않습니다. 심볼릭 링크는 거부합니다. 이미지 등 새 자산 형식이나 폴더가 필요하면 공개해도 되는지 검토한 후 허용 목록을 확장하세요.

모든 리소스 경로는 상대 경로이므로 프로젝트 저장소의 하위 경로에서도 동작합니다. 기본 시스템 글꼴을 사용하며, 배포 시 개발 도구나 `node_modules/`는 필요하지 않습니다. 로컬에서는 생성한 `artifacts/pages/`를 정적 서버로 열어 배포 파일을 미리 확인할 수 있습니다.

보안 관련 원칙과 게시 전 점검 방법은 [SECURITY.md](SECURITY.md)를 참고하세요. `.gitignore`는 앞으로의 실수로 인한 커밋을 줄이는 장치이며, 이미 추적되거나 Git 이력에 남은 비밀값을 제거하지는 않습니다.
